## 一、IAP（Google Play Billing）

### 1.1 你必须提供的东西

| # | 项目 | 用途 | 获取路径 |
|---|---|---|---|
| 1 | **Google Play 开发者账号** | 上架与内购必需 | play.google.com/console（$25 一次性） |
| 2 | **应用包名** | 唯一标识，创建后不可改 | 自行确定，如 `com.yourco.flozeclone` |
| 3 | **12 个消耗型商品 ID** | hearts 充值档位 | Play Console → 应用内商品 |
| 4 | **服务账号 JSON 密钥** | 服务端校验订单真伪 | Google Cloud Console → IAM → 服务账号 |
| 5 | **许可测试账号** | 沙盒测试不扣真实款 | Play Console → 测试 → 许可测试 |
| 6 | **Android 签名密钥** | 上传 APK/AAB | 自行生成 keystore |

### 1.2 商品配置规格（对齐 FlOZE 实测）

```
商品 ID    floze.heart.plan1 … floze.heart.plan12
商品类型   消耗型（Consumable）      ← 关键：必须可重复购买
价格区间   $2.99 – $99.99
```

**为什么必须是"消耗型"**：hearts 是虚拟货币，用户会反复购买。若配成"非消耗型"，
用户买过一次就无法再买同一档。这是最常见的踩坑点。

### 1.3 服务端校验（防盗刷）

```
POST https://androidpublisher.googleapis.com/androidpublisher/v3/applications/
     {packageName}/purchases/products/{productId}/tokens/{token}
Authorization: Bearer {服务账号签发的 access_token}
```

**必须校验**，否则客户端伪造回调即可白拿 hearts。复刻代码中对应位置：
`server.py` 的 `Store.add_hearts()` 调用点 —— 目前是模拟发放，
接入后应改为「校验通过才发放」。

### 1.4 掉单补偿（FlOZE 的 `heart-unhandle` 机制）

FlOZE 以 `{txId, planId}` 记录未处理交易，启动时补偿。复刻已建模此结构，
接入时需要：

- 客户端购买成功后立即上报交易（不等服务端回调）
- 服务端校验失败时**先记录**，人工/定时重试
- 避免「已扣款未到账」的客诉

## 二、广告 SDK

### 2.1 AdMob（当前复刻的默认路径）

| # | 项目 | 用途 | 获取路径 |
|---|---|---|---|
| 1 | **AdMob 账号** | 广告变现主体 | admob.google.com |
| 2 | **App ID** | 形如 `ca-app-pub-XXXXXXXXXXXXXXXX~YYYYYYYYYY` | AdMob → 应用 → 应用设置 |
| 3 | **Ad Unit ID（激励视频）** | 换 hearts 的广告位 | AdMob → 广告单元 → 激励广告 |
| 4 | **收款信息** | 结算 | AdMob → 付款 |
| 5 | **UMP / GDPR 同意配置** | 欧盟合规必需 | AdMob → 隐私与消息 |

**FlOZE 实测的 AdMob App ID**（供你参考格式，不可直接复用）：
`ca-app-pub-3455649885778345~4184682196`

### 2.2 Pangle（可选，字节系）

| 项目 | 用途 |
|---|---|
| Pangle 账号 + 开发者认证 | 广告平台接入 |
| App ID / Placement ID / Slot ID | 广告位标识 |

FlOZE 实测使用 Pangle **8.1.0.4**，并带 TikTok 归因（`api16-access-ttp.tiktokpangle.us`）。

### 2.3 Meta Audience Network（可选）

| 项目 | 用途 |
|---|---|
| Meta for Developers 账号 | 平台接入 |
| App ID + Placement ID | 广告位标识 |
| Business Manager 绑定 | 结算 |

### 2.4 三网并行的实际意义

FlOZE 同时接了三家 —— 这不是冗余，而是：
- 追求 eCPM 最大化（按地区择优）
- 填充率互补（某家在某地区可能无库存）
- 服务端可通过 `policy.unit` 动态调整流量分配（复刻已实现该开关）

**建议起步只接 AdMob**，验证变现模型后再扩。

## 四、拿到凭证后填入哪里

复刻代码已预留接入点：

```python
# llm.py          → 模型凭证（MINIMAX_API_KEY 环境变量）
# server.py       → API.ad_reward()        广告奖励发放（当前模拟）
#                   API.prepare_send()     hearts 校验（当前直连本地库）
# store.py        → heart_ledger 表        已支持 txId/planId 结构
```

**接入顺序建议**：
1. 广告（改动小，见效快，能立刻验证免费用户变现）
2. IAP（需要 Play 账号与技术栈调整，周期长）
3. 服务端订单校验（可与 IAP 同期做）

## 五、合规红线（不要省）

- **CSAM 零容忍** —— 与内容尺度是两件事，必须服务端拦截
- **年龄门禁** —— Mature 17+ 分级要求
- **广告同意管理（UMP）** —— 欧盟必需，否则广告平台会限流
- **数据保留策略** —— "No data shared with third parties" 的声明必须与实际一致
