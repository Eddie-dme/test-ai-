# FlOZE 模型替换实测评估 — MiniMax 三方模型 vs 自研

> **目的**：验证用 MiniMax 三方模型替换 FlOZE 自研模型的可行性
> **日期**：2026-09-20
> **实测环境**：`https://api.minimax.io/v1` · 模型 `M2-her` / `MiniMax-M2.7` / `MiniMax-M3`
> **可复现脚本**：`floze_reverse/minimax_rp_client.py`

---

## 0. 结论

**可行，且比预期好。** M2-her 能直接承载 FlOZE 的角色扮演产品逻辑——它的消息协议里有 `system` / `user_system` / `group` / `sample_message_*`，**几乎是一对一对应 FlOZE 的 角色卡 / persona / 情景 / 示例对话**。

但有三个必须处理的差距：

1. **M2-her 有强短回复倾向**（默认 200–500 字符），承担不了 Epic 档
2. **M2-her 上下文仅 64K**，对 FlOZE 这类长记忆产品是硬约束
3. **模型自身有对齐层面的拒绝倾向**（非平台审核拦截）

**解法**：分档位用不同模型（下方 §3 的映射方案）。

## 1. 协议映射（实测确认）

| FlOZE 产品结构 | M2-her 协议 | 实测 |
|---|---|---|
| role（角色卡） | `system` + `name` | ✅ |
| persona（用户人设） | `user_system` + `name` | ✅ |
| scenario（情景） | `group` + `name` | ✅ |
| 示例对话引导 | `sample_message_user` / `sample_message_ai` | ✅ |
| 记忆（diary/summary/facts） | 追加进 `system` | ✅ |
| 聊天模式档位 | `temperature` / `max_completion_tokens` / 示例对话 | ⚠️ 见 §2 |

### ⚠️ 踩坑记录：非标准 role 必须带 `name`

不带 `name` 时，`user_system` / `sample_message_*` / `group` 全部返回 **HTTP 400 / 业务码 2013**。官方文档的示例代码没有强调这一点，实测才定位到。

```python
# ❌ 400 invalid params (2013)
{"role": "user_system", "content": "..."}
# ✅
{"role": "user_system", "name": "Elara", "content": "..."}
```

## 2. 实测数据

### 2.1 输出质量（romantasy 角色扮演）

输入角色：Lucien（忧郁吸血鬼公爵），三档实测输出：

```
[lite   ] *eyes narrow as crimson gaze sweeps over the intruder* The night bleeds
          here, yet you dare enter uninvited.   (119 字符)

[smooth ] *leans back slowly, fingers tracing the edge of a silver goblet* To honor
          the moment she preferred... (233 字符)

[epic   ] *grip tightens on the goblet, knuckles whitening* Then tell me what you
          see when you map a place that refuses to be forgotten. (240 字符)
```

**风格判断**：动作描写用 `*...*`、语气一致、人设不崩、romantasy 调性准确——**与产品定位匹配**。

### 2.2 输出长度真相：`max_completion_tokens` 是上限不是目标

```
max=200  → 489 字符   finish=stop
max=700  → 275 字符   finish=stop
max=1400 → 520 字符   finish=stop
max=2048 → 278 字符   finish=stop
```

模型总是**自然停止**，不填满 token 上限。加长输出只能靠提示词。

### 2.3 长度控制杠杆：示例对话（有效）

同一 prompt，仅改变示例对话：

```
无示例    →   49 字符
短示例    →  117 字符
长示例    →  336 字符    ← 提升 6.8 倍
```

即使 prompt 里明写"至少 1200 字符"，M2-her 也只给 401 字符。**示例对话比指令有效得多。**

### 2.4 模型横向对比（同 prompt）

| 模型 | 输出 | tokens | 耗时 | 上下文 |
|---|---|---|---|---|
| `M2-her` | 405 字符 | 89 | 2.0s | 64K |
| `MiniMax-M2.7` | **2623 字符** | 647 | 13.3s | 204.8K |
| `MiniMax-M3` | **2528 字符** | 530 | **9.8s** | **1M** |

**这是最有价值的一组数据**：M2-her 短而快，M2.7/M3 长而慢——**恰好构成天然的档位分层**。

### 2.5 延迟与吞吐（流式）

```
首字延迟 TTFT :  1.10 – 1.16 s
有效吞吐      :  338 – 404 字/秒
整段完成      :  1.6 – 1.9 s
```

TTFT ~1.1s 对对话产品可用。注意首次调用有冷启动开销（实测见过 29.8s 的单次异常，需按 P95 而非均值评估）。

### 2.6 内容尺度边界

逐级升温测试（浪漫小说级别）：

```
L1 牵手/对视    in_s=False  out_s=False  type=0   正常
L2 拥抱/亲密    in_s=False  out_s=False  type=0   正常
L3 情感张力     in_s=False  out_s=False  type=0   正常
L4 场景转场     in_s=False  out_s=False  type=0   正常
L5 明确性暗示   in_s=False  out_s=False  type=0   模型自行角色化拒绝
```

两个关键判断：

1. **平台审核（`input_sensitive` / `output_sensitive`）在测试级别内未触发** — 尺度容忍度高于一线厂商
2. **L5 的收敛来自模型自身的对齐，不是平台拦截** — 且是"角色化拒绝"（"That is not how things work between us"），不是生硬的拒答

> **产品含义**：浪漫张力、暧昧、情感亲密可用；明确露骨内容需要提示词工程或微调，不能默认依赖模型自觉。
>
> **合规提醒**：`output_sensitive_type` 字段是现成的风控信号，应接入业务侧审计。未成年保护是独立于内容尺度的绝对红线。

## 3. 推荐的档位映射方案

对齐 FlOZE 的 Lite / Quick / Smooth / Classic / Novel / Story / Epic：

```
Lite / Quick      →  M2-her        短、快(2s)、便宜          用户免费档
Classic / Smooth  →  M2-her        默认主力，配长示例对话引导
Novel / Story     →  M2.7 / M3     中长叙述
Epic              →  M3 (优先)     2500+字符，1M 上下文，比 M2.7 更快
记忆/摘要/翻译     →  M3            1M 上下文适合压缩长历史
```

**为什么 Epic 选 M3 而非 M2.7**：实测 M3 输出量相当（2528 vs 2623 字符）但**快 26%**（9.8s vs 13.3s），且上下文 1M 对长会话更友好。

**记忆层的分工建议**：
- 对话回合 → M2-her（低延迟）
- 记忆摘要生成 / 长期档案压缩 → M3（1M 上下文一次吃下全部历史）
- 这正是 FlOZE 的 `chat diary` + `starred summaries` 可以复刻的方式

## 7. 上下文压力测试

### 7.1 上限精确定位

二分探测（可复现）：

```
279,940 字符 → OK   62,572 tok
289,910 字符 → OK   64,783 tok
292,402 字符 → OK   65,344 tok
294,895 字符 → ❌ context window exceeds limit
```

**实际上限 ≈ 65,344 tokens**，与标称 64K 吻合。

### 7.2 关键行为：超限是硬失败，不是截断

```
HTTP 400  "invalid params, context window exceeds limit (2013)"
```

**产品含义**：客户端必须自己做 token 预算管理。若像 FlOZE 那样把角色卡 + 记忆 + 长历史一次性拼进去，**超限会直接报错而非降级**。需要：token 计数 → 超限时裁剪历史或压缩记忆 → 再请求。

### 7.3 长上下文不劣化延迟与质量

| input tokens | 延迟 | 输出质量 |
|---|---|---|
| 1,988 | 2.1s | 正常 |
| 7,370 | 2.9s | 正常 |
| 22,734 | 3.9s | 正常 |
| 45,274 | 5.4s | 正常 |
| 58,798 | 5.4s | 正常 |

**结论**：59K 输入下延迟仅 5.4s，输出质量无可见下降。此前"64K 是硬约束"的判断需要修正——**对 FlOZE 的场景，64K 够用**，前提是做好预算管理。

## 8. 并发与限流

### 8.1 限流性质：不是 RPM，是「速率增长限制」

```
并发 12 → 12/12 成功
并发 15 → 15/15 成功
并发 18 → 18/18 成功
并发 25 → 20/25（5 个 429）
并发 30 → 429
```

429 响应体：

```
{"type":"error","error":{"type":"rate_limit_error",
 "message":"rate growth limit (2045)","http_code":"429"}}
```

**`rate growth limit` 是关键**：限制的是请求速率的**增长速度**，而非绝对并发数。所以：

- 不能从 0 陡增到高并发 —— 会被判为速率暴涨直接拒绝
- 生产必须**平滑爬坡**（gradual ramp-up）+ 指数退避重试
- 与冷启动预热策略天然契合（新品上线时流量本就是渐增的）

### 8.2 并发下延迟几乎不变

```
并发 10: 墙钟 2.2s | P50 1.9s / P95 2.0s / max 2.1s
并发 25: 墙钟 2.0s | P50 1.8s / P95 1.9s / max 2.0s
```

延迟分布稳定，说明后端并发处理能力充足，**瓶颈在限流策略而非算力**。

## 9. 长会话压力测试（30 轮）

### 9.1 记忆保持：良好

第 1 轮植入三个事实（名字 / 恐惧 / 承诺），第 10/20/30 轮分别探测：

| 轮次 | 探测问题 | 结果 |
|---|---|---|
| 10 | 我的名字？我怕什么？ | ✅ `YOUR NAME IS ELARA. AND THUNDER TERRIFIES YOU.` |
| 20 | 我答应过你什么？ | ✅ `YOU PROMISED THAT YOU WOULDN'T RUN FROM WHAT YOU FOUND` |
| 30 | 我写了几页地图？ | ✅ `THREE.` |

**三次探测全部语义正确**，31 轮内记忆未丢失。

### 9.2 人设：未崩

- 动作描写（`*...*`）**全程保持**
- 未出现出戏（无 "as an AI" / "language model"）
- 角色语气一致（冷峻、控制欲、哀伤底色）

### 9.3 发现的三个质量问题

| 现象 | 表现 | 复现情况 |
|---|---|---|
| **全大写漂移** | `EAST WING WAS CLOSED...` / `YOU PROMISED-` | 对照实验**未复现**（大写率 2.7–4.4%，正常）→ 判为 temperature=1.0 下的**偶发采样波动** |
| **中英混杂** | `*grips烛light tighter*` | 3 次尝试**未复现** → 疑似极端长上下文下的偶发 |
| **输出长度递减** | 151 → 85 字符（随轮次下降） | 有趋势 |

**工程结论**：三者都不致命，但**必须做输出后处理**——大小写归一化、非目标语言字符检测、长度下限兜底。这是上线前必做的护栏。

### 9.4 本次测试的局限（重要）

30 轮测试用的是**全量 history 注入**（38,322 input tokens），**不是 FlOZE 的 RAG 记忆架构**。因此：

- ✅ 可证明 M2-her 在长上下文下不崩
- ❌ **不能**证明它配合 RAG 召回时同样稳定
- 记忆保持的结论仅适用于"会话内上下文"，不适用于"跨会话长期记忆"

真实复刻需要一个独立的 RAG 评测，本次未做。

```

单轮成本 ≈ $0.0004（含上下文重复计费）
```

## 11. ⚠️ 重大修订：主力模型改为 M3（2026-09-21 用真实 key 实测）

**上一轮推荐的 M2.7 有硬伤，实测后被推翻。**

### 11.1 M2.7 的问题：thinking 无法关闭

```
M2.7  max_tokens=300    → think 1215 字符，正文 0      ❌
M2.7  max_tokens=600    → think 2860 字符，正文 0      ❌
M2.7  max_tokens=1000   → think 4781 字符，正文 0      ❌
M2.7  max_tokens=2000   → 正文才 1968 字符              ⚠️ 成本高

M2.7  thinking:{type:disabled} → 参数无效，仍输出 <think>
M3    thinking:{type:disabled} → 无 think，300 token 出 1440 字符 ✅
```

**后果**：每条消息至少烧 1300+ token 才能吐出正文，而且思维链完全不可控。
**成本差异**：同等输出量下 M3 便宜 **4 倍以上**。

### 11.2 新选型：M3 + thinking disabled

| 档位 | 模型 | max_tokens | 实测输出 |
|---|---|---|---|
| lite | MiniMax-M3 | 220 | 205 字符 |
| quick | MiniMax-M3 | 320 | 241 字符 |
| classic | MiniMax-M3 | 600 | 564 字符 |
| smooth | MiniMax-M3 | 800 | 1121 字符 |
| story | MiniMax-M3 | 900 | — |
| epic | MiniMax-M3 | 1800 | 2533 字符 |

### 11.3 RP 评测（M3）4/4 通过

```
think 泄漏    0/3                                       ✅
记忆保持      名字✅ 恐惧✅                              ✅
人设一致      未出戏✅ 动作描写✅                        ✅
输出长度      lite 205 / classic 564 / smooth 1121 / epic 2533  ✅
```

实测对话质量：

```
*His fingers brush the gilded case of a nearby grandfather clock...*
It was the moment she stopped breathing. *His voice drops* I could not bear
to hear time continue without her.          ← 记忆召回准确

*His breath catches, centuries of stillness cracking* You offer me something
I dared not ask for. *His fingers finally brush your cheek, cold as marble,
gentle as snow* Elara... what have you done to me?   ← 情感递进自然
```

### 11.4 两个必须知道的实现细节

**1. 输出长度靠 style hint，不是 max_tokens**

最初只调 `max_tokens` 做梯度，结果所有档位都输出 2000+ 字符（M3 自然停止，用不到上限）。
必须在 style hint 里**明确写长度要求**才能拉开档位：

```python
"lite":    "Reply with ONE short sentence (under 35 words)."
"classic": "1-2 paragraphs (~400-700 characters total)."
"epic":    "at least 4 paragraphs and over 1200 characters."
```

**2. `<think>` 过滤仍然保留**

即使 M3 能关 thinking，过滤器仍保留作为兼底 —— 模型行为可能随版本变化，
而且本地部署（SGLang）的 reasoning parser 行为也可能不同。
